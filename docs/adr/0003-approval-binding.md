# ADR 0003: 승인의 결합 대상과 위협 모델

- 상태: 제안(#8 후속). 2026-10-28, 기준 `origin/feat/8-land` `e00f39a`. 사람 검토·병합 전입니다.
- 범위: `packages/filesystem/src/approvals.ts`(`savePlan`·`issueApproval`·`consumeApproval`·`ApprovedBatch`)와 `packages/engine/src/plan.ts`(`buildPlan`)의 현재 동작을 결정으로 기록합니다. 실행기(#10–#12)는 범위 밖입니다.
- 근거: #8 독립 검증(verify-8)의 관측 O-1~O-7. 검증 수준은 macOS(이 Mac) 단위 검증이며 Windows는 미검증(CI 대기)입니다.

## 결정 1: 승인은 저장된 계획의 세션과 루트 식별에 결합한다 (O-5, O-6)

승인 기록(`approvals/<id>.json`)은 다음에 결합합니다.

| 결합 대상 | 값의 출처 | 소비 때 확인 |
| --- | --- | --- |
| 계획 | `planId`(= 계획 내용의 sha256) | 저장 계획을 다시 해시해 ID와 같아야 함, 승인의 `planId`·`rootGrantId`·`sessionId`·`profileId`·`profileRevision`과 계획이 같아야 함 |
| 작업 묶음·방식 | 정렬된 `operationIds`, `mode` 하나 | 계획의 부분집합이고 모두 그 방식의 종류여야 함(`MODE_MISMATCH`) |
| 세션 | **계획의** `sessionId`(계획을 만든 프로세스의 세션) | 승인·계획·저장 루트 식별의 `sessionId`가 서로 같아야 함 |
| 루트 식별 | 저장 계획의 `canonicalPath + device + inode` | 소비하는 프로세스가 같은 경로로 폴더 권한을 다시 발급하고 dev/inode가 같아야 함 |
| 개인 규칙 | `profileId` + `profileRevision` | 저장 프로필이 같은 ID·revision의 confirmed 상태여야 함 |
| 유효 기간 | 발급 + 10분(계획 만료를 넘지 않음) | 만료·발급 전 시각 거부, `.used` 표시가 있으면 `APPROVAL_USED` |

**소비하는 프로세스의 세션은 대조하지 않습니다(O-6).** CLI는 `plan`, 승인, `apply`가 서로 다른 프로세스이고, 폴더 권한(`RootGrant`)은 프로세스 메모리에만 있어 프로세스를 넘어 재사용할 수 없습니다. 그래서 세션 결합은 "승인이 그 계획을 만든 세션의 것"이라는 뜻이고, 실행 프로세스는 저장된 세션 ID로 루트 권한을 새로 발급합니다(`ApprovedBatch.grant`).

**같은 폴더를 다시 선택해도 기존 승인을 무효화하지 않습니다(O-5).** 같은 경로·같은 dev/inode의 폴더를 다시 고르면 새 폴더 권한(다른 salt, 다른 `id`)이 생기지만, 승인은 계획 때의 `rootGrantId`와 저장된 루트 식별에 묶여 있어 그대로 쓸 수 있습니다. 프로세스 간 실행을 지원하려면 "다시 선택"과 "다음 명령에서 같은 폴더를 연 것"을 구분할 수 없기 때문입니다.
대신 **폴더 교체·이동은 거부합니다.** 같은 경로에 다른 폴더(다른 dev/inode)가 있거나 링크로 바뀌었거나 사라졌으면 승인 발급·소비가 `FILE_CHANGED`로 실패합니다. 다른 폴더를 선택하면 다른 계획 ID가 필요하므로 이전 승인으로는 그 폴더를 다룰 수 없습니다.

### ARCHITECTURE.md 불변 조건 3과의 차이

`docs/ARCHITECTURE.md` 불변 조건 3은 "폴더 재선택 … 은 실행을 거부합니다"라고 적고 있습니다. 현재 구현과 이 ADR은 **같은 폴더(dev/inode 동일)의 재선택은 거부하지 않고, 다른 폴더로의 교체·이동만 거부**합니다.
이 ADR은 ARCHITECTURE.md를 고치지 않습니다. 계획 문서 담당에게 다음 문구 변경을 **제안**합니다.

> 3. **승인 결합**: 선택 작업·내용·대상·삭제 모드·계획 세션·루트 식별(경로+dev/inode)을 승인에 결합합니다. 다른 폴더로의 교체·이동, 규칙 변경, 파일 변경, 만료·재사용은 실행을 거부합니다. 같은 폴더를 다시 연 것(dev/inode 동일)만으로는 승인을 무효화하지 않습니다(ADR 0003).

INTERFACES.md에도 "세션 결합 = 계획의 sessionId, 소비 프로세스 세션은 대조하지 않음"을 적을 것을 함께 제안합니다.

## 결정 2: 승인 소비는 파일을 다시 확인하지 않는다. 실행 직전 재검증은 executor 책임 (O-1)

`consumeApproval`은 승인·계획·프로필·루트 식별만 확인하고 **작업 대상 파일을 stat하지 않습니다.** 반환된 `ApprovedBatch.operations[].expected`(크기·mtime·dev/inode·sha256)는 계획 때 본 값입니다.
승인 소비와 실행 사이에도 파일이 바뀔 수 있으므로, 원본 재검증(lstat 식별·크기·mtime, nlink 1, 링크 아님, 루트 안 실제 경로, 부모 링크 없음, `expected.sha256`이 있으면 재해시)은 executor(#10–#12)가 각 작업 직전에 해야 합니다. 변경된 파일 거부는 executor의 필수 테스트입니다. 같은 내용이 `ApprovedBatch` 주석에도 있습니다.

## 결정 3: 위협 모델 — 상태 폴더에 쓸 수 있는 사람은 범위 밖 (O-2, O-3)

- 승인 기록에는 상태 폴더 비밀(`<state>/secret`, 0600)로 만든 HMAC이 있습니다. CLI 인수·GUI·손으로 만든 JSON처럼 비밀을 모르는 작성자가 만든 승인은 유효한 계획을 가리켜도 거부됩니다. `usedAt`은 MAC에서 빼고, 재사용은 `O_EXCL`로 만드는 `<id>.used` 표시로 막습니다.
- 계획 파일에는 MAC이 없습니다. 계획 ID가 내용 해시이므로 내용을 바꾸면 ID가 달라져 기존 승인과 맞지 않습니다.
- **상태 폴더에 쓸 수 있는 프로세스·사람(같은 OS 사용자)은 방어 범위 밖입니다.** 그런 작성자는 비밀을 읽어 새 승인을 만들거나, `.used`를 지우고 JSON을 되돌려 승인을 다시 쓸 수 있습니다(O-3). 같은 사용자 권한으로 사용자 파일을 직접 지울 수도 있으므로 승인 파일만 강화해서 얻는 이득이 작다고 판단했습니다.
- 2차 기록은 #13의 저널입니다. 실행은 작업마다 `intent`를 먼저 기록하고 같은 op의 성공을 다시 실행하지 않으므로, 되돌린 승인으로 같은 작업을 재실행하려는 시도를 저널 대조로 찾을 수 있게 하는 것을 executor/복구 담당에게 제안합니다(현재 미구현·미검증).

## 결정 4: 마지막 사본 삭제는 명시적으로만 (O-4)

`buildPlan`은 내용이 같은 파일 묶음(해시가 같은 2개 이상)의 **모든** 사본이 삭제 대상이 되면 `KEEPER_INVALID`(메시지에 "마지막 사본")로 거부합니다. `allowLastCopy: true`일 때만 허용하고, 그 작업의 `reason`에 마지막 사본 삭제임을 적습니다(`LAST_COPY_REASON`). CLI는 `--delete-last-copy`가 있을 때만 이 옵션을 넘깁니다.
중복 후보 삭제(`deleteSelections`)는 원래 keeper를 남기므로 해당하지 않습니다. 해시하지 않은 단일 파일(크기가 같은 파일이 없거나 빈 파일)과 내용이 유일한 파일의 명시 삭제는 그대로 허용합니다. 보호된 참고 파일은 해시하지 않으므로 남는 사본으로 세지 않습니다(보수적).

## 결정 5: 잘못된 입력은 AfoError 코드로 (O-7)

- `savePlan`의 계약 위반 계획 → `PLAN_CHANGED`.
- `issueApproval`의 잘못된 요청 형태(null·문자열·배열·추가 필드)·잘못된 `now`(Date가 아님, NaN) → `APPROVAL_INVALID`. `consumeApproval`의 잘못된 `now`도 `APPROVAL_INVALID`이며 승인을 소비하지 않습니다.
- 영구 삭제 확인 문구는 **NFC 정규화 후** `영구 삭제`와 비교합니다. 조합형(NFD)으로 입력한 같은 문구는 허용합니다(현 동작 유지).

## 남은 위험

- 프로세스 간 실행에서 "같은 폴더를 다시 선택"을 승인 무효화 사유로 쓰지 않으므로, 폴더를 다른 곳으로 옮겼다가 같은 경로로 되돌려 놓은 경우(dev/inode 동일)도 같은 폴더로 취급합니다. 그 사이 안쪽 파일의 변화는 executor의 실행 직전 재검증에만 의존합니다.
- 상태 폴더 쓰기 권한자에 대한 방어는 없습니다. 저널 기반 2차 탐지는 미구현입니다.
- Windows에서 dev/inode(`ino`)의 안정성은 미검증(CI 대기)입니다.
