# 병합 PR 검토에서 확인한 결함 수정

날짜: 2026-10-26. 기준: `6ad48a05a10b09e4520e94155edbc9bd8a48cd6e`.
관련 이슈: #13(잠금·복구), #25(Firebase). 이번 사용자 지시는 검토에서 발견한 다섯 결함의 수정과 PR 작성이다. 전체 이슈 완료·배포·병합을 뜻하지 않는다.

## 수정 계약

1. `withRootLock`, `readRootLock`, `rootLockFile`의 두 번째 인수는 `{ device, inode }`다. RootGrant 자체를 전달할 수 있다. 선택마다 바뀌는 `grant.id` 문자열은 거부한다. 같은 실제 폴더의 독립 발급 권한과 별도 프로세스는 같은 잠금을 사용한다. 폴더 권한·승인은 별도 실행 계층 책임이다.
2. Windows가 파일 아래 경로를 `ENOENT`로 보고해도 잠금의 기존 상위 경로가 일반 폴더인지 검사한다. `locks`가 파일이면 free로 처리하지 않는다.
3. 복구는 계획과 저널의 식별을 대조하고 실제 파일의 dev/inode·크기·수정 시각·계획에 있는 SHA-256을 확인한다. 해시는 streaming으로 읽으며 점검 전후 파일·상태 manifest를 비교한다. 자동 재실행·삭제·원복은 하지 않는다.
4. Firebase 저장 v2는 불변 세대별 규칙 문서를 부모 transaction에서 전부 검증한다. 존재하지 않는 참조, 현재 세대 문서의 수정·삭제, 부모 문서 직접 삭제를 거부한다. 최대 20개 규칙을 유지한다.
5. 삭제는 버전을 증가시킨 tombstone을 남긴다. 같은 ID 재생성 뒤 이전 버전의 저장과 삭제는 실패한다. 부모 공개 후 이전 세대 정리는 별도 배치이며 실패 시 `CleanupPending.committedRevision`으로 이미 반영된 결과를 알린다. `cleanup(id)` 재시도는 현재 세대를 지우지 않는다.

## 호환성과 한계

- 잠금 API의 인수와 파일 키가 바뀌었다. 실행기 연결 시 실제 검증한 RootGrant를 전달해야 하며 이전 버전과 동시에 실행하지 않는다. 기존 잠금을 자동으로 지우거나 이관하지 않는다.
- 공개용 규칙 JSON은 v1을 유지하고 Firestore 저장만 v2로 변경했다. 기존 v1 저장 자료는 자동 변환하지 않으며 명시적 오류를 반환한다. 운영 자료 마이그레이션·규칙 배포는 이 PR에서 수행하지 않는다.
- 부모의 현재 세대 공개는 원자적이다. 이전 세대 정리는 공개 후 진행되므로 네트워크 실패 시 이전 문서가 남을 수 있다. 이때 과거 버전의 save/remove를 그대로 반복하면 안 된다. tombstone에는 원래 이름·규칙을 남기지 않고 버전과 고정 이름을 보존한다.
- 기존 stale 잠금의 세 프로세스 인수 경쟁, PID 재사용, OS 경로 교체 경쟁 한계는 이번 다섯 결함 수정으로 해소됐다고 주장하지 않는다.
