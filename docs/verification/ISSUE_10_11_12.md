# #10·#11·#12 실행기: 이동·OS 휴지통·선택 영구 삭제·이동 되돌리기

상태: **구현 + 단위 검증(이 Mac의 합성 temp 폴더)**. 2026-10-26, 기준 commit `1f17428`, core-builder 작성.
승인 발급·소비(#8, `consumeApproval`)와 루트 잠금(#13, `withRootLock`)은 이 기준에 없습니다. CLI `apply/undo/runs` 연결은 interface-builder 범위입니다.
아래 "검증 결과" 절은 verifier가 독립 fixture로 작성합니다. 이 문서의 builder 실행 결과는 자기 검사이며 독립 검증이 아닙니다.

### 배치 사전 검사 (실패 시 `AfoError`, 파일·저널·실행 기록 변경 없음)

1. `verifyGrant(grant, 'work')`, 계획·승인·작업의 스키마 재파싱. grant는 이 프로세스 재발급이므로 id가 아니라 `grant.canonicalPath === plan.rootPath`로 대조(grant의 dev/inode는 `verifyGrant`가 실제 폴더와 대조).
2. 상태 폴더 절대 경로·`assertStateDirOutside`.
3. `approval.planId === plan.id`, `approval.rootGrantId`가 `plan.rootGrantId` 또는 재발급 `grant.id`(아니면 `APPROVAL_INVALID`), 프로필 ID·버전 일치(`PROFILE_CHANGED`),
   `usedAt !== null`(`APPROVAL_INVALID`), `expiresAt > 지금`(`APPROVAL_EXPIRED`), `operations`가 `approval.operationIds`와 순서·개수까지 같음(`APPROVAL_INVALID`),
   각 작업이 plan의 같은 ID 작업과 deep-equal(`PLAN_CHANGED`), 모든 kind가 `approvalModeKind[mode]`(`MODE_MISMATCH`).
4. 승인별 배타 표시 `runs/<approvalId>.approval`을 `open(O_CREAT|O_EXCL)`로 생성. 이미 있으면 `APPROVAL_USED`(같은 승인으로 두 번째 실행 불가, 다른 프로세스 포함).
5. `runs/<runId>.json`(report null) 저장. 실패하면 파일 변경 전에 `JOURNAL_FAILED`/`DISK_FULL`.

plan hash 재계산과 plan 만료 확인은 `consumeApproval`(#8) 몫으로 두고 여기서 하지 않았습니다.

### 작업마다 (순서대로, 병렬 없음)

취소 확인 → 저널 `intent`(fsync) → `faultInjection('after-intent')` → 원본 재검증 → OS 작업 → `faultInjection('after-op')` → 독립 확인 → `faultInjection('before-done')` → 저널 `done`/`failed` → `onProgress`.

- 원본 재검증(CARRYOVER O-1): 루트 lstat(dev/ino = grant) → 루트부터 원본 부모까지 **모든 구성요소** lstat(실제 폴더·링크 아님·루트와 같은 dev) → 부모 realpath가 루트 안 →
  원본 lstat(일반 파일·링크 아님·nlink 1·dev/ino/size/mtimeNs = expected). `expected.sha256`이 있으면 64 KiB 스트리밍 재해시(O_NOFOLLOW, 열린 핸들 dev/ino/size 고정) 후 다시 lstat 비교. 불일치는 `FILE_CHANGED`.
- 이동: 목적지 부모를 루트에서 한 단계씩 확인하고 없으면 `mkdir`(non-recursive) 후 다시 lstat. 목적지가 있으면 `DEST_EXISTS`. 그다음 `linkMoveNoClobber`(덮어쓰기 없음).
  독립 확인: 원래 경로 부재 + 목적지 dev/ino/size/nlink 1 + 목적지 sha256. 해시는 `expected.sha256`이 없어도 계산해 저널 `done.after.sha256`에 기록합니다(되돌리기가 이후 편집을 감지하도록).
- 휴지통·영구 삭제: `keeper`가 있으면 그 경로도 같은 부모 체인 검사 + 일반 파일·링크 아님·nlink 1·원본과 다른 inode·sha256 = `expected.sha256`. 아니면 `KEEPER_INVALID`, 파일 변경 없음.
  `keeper: null` delete는 사용자가 명시적으로 고른 파일로 허용합니다. 휴지통 실패는 영구 삭제·재귀 삭제로 우회하지 않고 재시도하지 않습니다. 영구 삭제도 실패 후 재시도하지 않습니다.
- 상태 판정: 성공은 독립 확인 후에만 `moved/trashed/deleted`. OS 호출이 실패하면 원본이 같은 inode·nlink 1로 그대로 있고 목적지가 그 inode가 아닐 때만 `failed`, 아니면 `unknown`.
  어댑터 `UNKNOWN`과 확인 실패도 `unknown`. OS 호출 전 실패는 모두 `failed`. 실행하지 않은 항목은 `skipped`.
- 취소: 시작한 작업은 끝까지 마치고, 남은 작업은 저널 `skipped`(CANCELLED, 기록 가능한 동안) + 결과 `skipped`.
- 저널 실패: `intent`를 못 쓰면 그 작업 `failed`(`JOURNAL_FAILED` 또는 ENOSPC면 `DISK_FULL`), 남은 작업 `skipped`(같은 코드), 이후 파일 변경 없음.
  OS 작업 성공 뒤 `done`을 못 쓰면 결과는 확인된 상태(예: `moved`)로 두고 detail에 "저널 기록 실패(복구 검사 필요)"를 붙이며 남은 작업은 건너뜁니다.
- `faultInjection`이 throw하면 그 예외를 그대로 전파하고 저널·실행 기록을 더 쓰지 않습니다(`runs/<runId>.json`의 report는 null로 남음). `before-done`은 `done`과 `failed` 기록 직전 모두에서 호출됩니다. `after-op`은 OS 호출을 시도해 성공한 경우에만 호출됩니다.
- `onProgress`는 각 작업의 저널 기록이 닫힌 뒤 호출하며, 콜백 예외는 무시합니다.

### 공간 (#12)

`logicalBytesSelected` = 선택 작업 `expected.size` 합. `permanent-delete`일 때만 `freeSpace(root)`를 배치 전·후 관측해 `freeBytesBefore/After`, 그 외 모드는 null.
note는 모드별로: 이동은 공간을 확보하지 않음 / 휴지통은 확보량이 아니며 앱 내 자동 복구 없음(Finder·Windows 휴지통에서 직접 복원) / 영구 삭제는 되돌릴 수 없고 논리 크기·할당 크기 합·여유 공간 관측치는 서로 다른 값이며
다른 프로그램의 쓰기·스냅샷·clone 영향으로 정확한 회수량이 아님. 삭제 성공 항목 detail에 `st_blocks*512` 할당 크기 관측치(Windows는 "알 수 없음")를 따로 적습니다.

### 되돌리기

- 실행 기록 없음·실행 ID 형식 아님 → `APPROVAL_MISSING`. grant 경로가 실행 기록 루트와 다르면 `ROOT_FORBIDDEN`, dev/inode가 다르면 `FILE_CHANGED`. organize가 아닌 실행 → `NOT_SUPPORTED`(휴지통 복원은 사용자가 OS에서).
- 저널에 손상 줄이 하나라도 있으면 추측하지 않고 `STATE_CORRUPT`.
- 대상: `done` 이동 중 `undone`이 없는 것. 조건: 목적지 부모 체인 검사, 목적지가 링크 아님·nlink 1·`done.after`의 dev/ino/size와 같음, `after.sha256` 재해시 일치(아니면 `FILE_CHANGED`),
  원래 경로가 비어 있음(아니면 `DEST_EXISTS`). 원래 부모가 없으면 루트 안에서 한 단계씩 다시 만든 뒤 `linkMoveNoClobber(목적지, 원래 경로)`. 성공 status는 `moved`, detail "되돌렸습니다".
- 결과에서 빠지는 항목: 이미 `undone`인 작업(두 번째 undo는 아무것도 다시 실행하지 않고 빈 results), 원 실행에서 `failed`/`skipped`인 작업.
  `unknown`으로 보고하고 손대지 않는 항목: 원 실행에서 `intent`만 있는 작업, 이전 되돌리기의 `undo-intent`만 있거나 결과가 `failed`+`UNKNOWN`인 작업. 확인된 실패(`failed`+다른 코드) 후에는 다시 시도할 수 있습니다.
- 취소는 저널을 쓰지 않고 결과만 `skipped`(CANCELLED). 저널 실패 규칙은 실행과 같습니다.

### 저널 규약 (session C 복구 코드와 합의)

- 파일: `journal/<runId>.jsonl`(state.ts `journalFile`·`appendJournal`). 되돌리기는 같은 파일에 seq를 이어서 씁니다.
- 실행: `intent` → `done`(move는 `after` = 목적지 식별, sha256 포함) | `failed`(errorCode) | `skipped`(errorCode). `rootGrantId`는 `plan.rootGrantId`.
- 결과 불명: 저널에는 `failed` + `errorCode: 'UNKNOWN'`으로 닫습니다. **`failed`+`UNKNOWN`은 결과 불명일 수 있으므로 복구 검사 대상**입니다(OS 호출 전 알 수 없는 오류도 같은 코드라 보수적으로 취급).
- 되돌리기: `undo-intent`와 `undone`은 원래 이동과 **같은 `source`·`destination`·`before`** 를 씁니다(방향을 바꾸지 않음; 역방향은 phase가 뜻함). `undo-intent.after = null`, `undone.after` = 복원된 원래 경로의 식별(이동 때의 `after`와 같은 inode·size·sha256).
  실패한 되돌리기는 같은 opId의 `undo-intent` 뒤에 오는 kind `move`의 `failed` 항목입니다. 같은 opId에서 `undo-intent` 뒤의 `failed`/`skipped`는 원 실행이 아니라 그 되돌리기의 결과입니다.

### 상태 파일 (stateDir/runs/)

| 파일 | 내용 |
| --- | --- |
| `<approvalId>.approval` | `{"formatVersion":1,"approvalId","runId"}` 한 줄. `O_EXCL`로 만든 승인 재사용 방지 표시. 지우지 않음 |
| `<runId>.json` | `RunRecordSchema`: `formatVersion, runId, planId, approvalId, rootGrantId, mode, root{canonicalPath, device, inode}, operationIds, startedAt, finishedAt|null, report|null`. 시작 때 report null로 쓰고 끝에 report로 교체(`writeJsonAtomic`) |
| `<runId>.undo-<n>.json` | `UndoRecordSchema`: `formatVersion, runId, undoIndex(n≥1), startedAt, finishedAt, report`. 되돌리기 시도마다 새 파일, 원 실행 report는 덮어쓰지 않음 |

### 테스트 전용 옵션 (고정 인터페이스에 추가만 함)

- `ExecuteOptions.adapter?: Partial<ExecutorAdapter>`, `UndoOptions.adapter?`: `linkMoveNoClobber, moveToTrash, deleteFilePermanently, freeSpace, appendJournal` 대체.
  이 옵션을 쓴 테스트는 이름에 `(mock)`을 붙였고 OS 결과의 증거가 아닙니다(EXDEV, ENOSPC, 휴지통 성공·실패 모의). 영구 삭제 권한 테스트는 실제 함수를 감싸 호출 횟수만 셉니다.
- `ExecuteOptions.faultInjection` 은 DESIGN의 고정 인터페이스 그대로입니다.

### 함께 고친 것 (별도 커밋 `8cc7c2e`, CARRYOVER O-2)

`platform.ts`가 EPERM을 `NOT_SUPPORTED`로 보던 것을 `PERMISSION_DENIED`로 바꿨습니다(EACCES·EROFS도 같음; ENOTSUP·EOPNOTSUPP·ENOSYS·EMLINK는 `NOT_SUPPORTED`, EBUSY·ETXTBSY는 `FILE_BUSY`).
이 Mac에서 `chflags uchg` 합성 파일의 `link`·`unlink`가 EPERM이며 이동·영구 삭제가 `PERMISSION_DENIED`로 거부되고 manifest가 그대로임을 확인했습니다.
부작용: 하드링크를 지원하지 않는 파일시스템이 `link`에 EPERM을 돌려주면(Linux FAT 등으로 알려짐) 이제 `PERMISSION_DENIED`로 보입니다. macOS exFAT·Windows FAT의 실제 코드는 미검증입니다. ADR 0001 결정 2의 오류 매핑 문장은 이 커밋과 다르며 coordinator가 고칠 대상입니다.

## 한계와 미검증

- 루트 잠금 없음: `withRootLock`(#13, PR #30)이 기준에 없어 호출 자리에 TODO 주석만 둠. 잠금은 재진입 불가이므로 `executeBatch`/`undoRun` 바깥에서 한 번만 감싸야 합니다.
  참고: grant id는 발급마다 무작위 salt가 들어가므로 `grant.id`를 잠금 키로 쓰면 같은 폴더의 두 프로세스가 서로를 막지 못할 수 있습니다(잠금 키는 canonicalPath·dev/inode 기반이 안전). 잠금 담당 확인 필요.
- TOCTOU: 검사와 `link`/`unlink`/`mkdir`/휴지통 도구 사이에 다른 프로세스가 경로를 바꾸는 경쟁은 줄였을 뿐 없애지 못합니다(ADR 0001 결정 3).
- 만든 폴더 정리 없음: 이동이 실패하거나 되돌린 뒤에도 실행이 만든 빈 폴더는 지우지 않습니다(재귀 삭제 금지 원칙). 실패 detail에 만든 폴더 수를 적습니다.
- 실행 기록 크기: `writeJsonAtomic` 한도 1 MiB 때문에 작업이 수천 개를 넘으면 최종 report 저장이 실패할 수 있습니다. 이때 `RunRecordError`(report 포함)를 던지고 저널은 그대로입니다. 대량 실행 실측은 하지 않았습니다.
- 해시 비용: 이동은 목적지를 한 번 더 읽어 sha256을 기록하고(`expected.sha256`이 있으면 원본도 재해시), 큰 파일일수록 오래 걸립니다. 해시 중에는 취소하지 않습니다(시작한 작업은 끝까지).
- 이동 후 해시를 읽지 못하면(권한 등, `expected.sha256` 없음) `after.sha256: null`로 두며, 그 경우 되돌리기는 dev/ino/size로만 판단합니다.
- 실제 휴지통: macOS에서 executor 경로 1회 성공. **Finder 복원 실물 확인은 하지 않음**(GUI 조작 없음). Windows 휴지통·`OnlyErrorDialogs` 대화상자 가능성은 미검증.
- 교차 볼륨·disk full: 부모 체인의 dev 비교는 실제 코드 경로지만 두 번째 쓰기 가능 볼륨을 만들지 않아 실제 EXDEV·ENOSPC 파일 작업은 미검증(mock만).
- 재시작 후 확인(#12 완료 조건 일부): 실행 기록·저널은 파일로 남고 테스트가 새로 읽어 대조하지만, 실제 프로세스 재시작·`recover` 흐름은 #13 범위.
- 승인 일부 선택·영구 삭제 문구 확인 등 CLI 승인 화면은 #8/CLI 범위이며 여기서는 `ApprovedBatch`를 테스트 도우미로 만들었습니다.
