## 구현

- 단일 실행 파일에서 최신 정식 GitHub Release 확인. 이미 최신이거나 설치본이 더 새 버전이면 보존.
- OS·CPU에 맞는 릴리스 파일 존재 확인 → SHA-256 → 추출 → `--version` 확인 → 현재 실행 파일 교체.
- macOS는 실제 설치 경로로 심볼릭 링크를 해석하고 같은 볼륨에서 rename. Windows는 이전 실행 파일을 다른 이름으로 옮긴 뒤 새 파일 배치, 배치 실패 시 원래 이름 복원.
- 소스 실행본은 거부해 Node 실행 파일을 보호. 사용자 정리 대상·설정·규칙·계획·저널은 읽거나 수정하지 않음.
- 설치별 배타 잠금, 중간 설치 파일 변경 감지, 취소, 다운로드 크기·시간·리디렉션 제한. 네트워크 재시도 없음.
- 공개 릴리스·병합·배포, 실제 사용자 설치본 변경은 이번 범위에 포함하지 않았습니다. 명령이 없는 예전 설치본은 새 릴리스 이후 설치 스크립트를 한 번 다시 실행해야 합니다.

## Physical-device-verified / 실제 하드웨어 검증: 로컬 배포 fixture

실제 Mac에서 두 개의 SEA 단일 실행 파일을 만들고 전용 temp 설치 폴더로 검사했습니다.
**테스트용 0.2.0·0.3.0은 모두 이번 업데이트 코드에서 만든 빌드입니다.** 0.2.0은 버전 상수와 package.json의 버전만 임시 변경해 빌드한 뒤 원복했습니다. 공개된 과거 릴리스가 스스로 이 명령을 지원한다는 뜻이 아닙니다.

실행 순서:

```sh
npm run release:build -- --targets darwin-arm64 --out <새 빌드 폴더>
# 별도 테스트 빌드에서 version.ts와 package.json을 0.2.0으로 바꿔 같은 빌드 명령을 실행하고 즉시 원복
node scripts/release/verify-update.mjs --old <0.2.0 압축 파일> --new <0.3.0 압축 파일>
```

검증 스크립트는 Node.js에서 로컬 HTTP 서버를 띄우고, 공백·한글이 있는 임시 설치 경로와 PATH 심볼릭 링크를 만든 뒤 실제 설치본의 `update` 명령을 실행합니다. 전경 창·입력·사용자 설치본은 사용하지 않았습니다.

관측 결과:

- 0.2.0 설치본의 `afo update` 종료 0, 다음 `--version`은 `afo 0.3.0`.
- 설치 실행 파일의 SHA-256이 새 압축 파일에서 독립적으로 추출한 실행 파일과 일치: `13b6a10965a6275e812b37a0da3567a34d5917a33a7851005fcae0e1e370e382`.
- 다시 `update`: "이미 최신", 메타데이터 요청 1회만 수행.
- 합성 구버전 복원 후 잘못된 체크섬 제공: 종료 1, 설치 실행 파일의 전후 해시·0.2.0 버전 보존.
- 합성 규칙 sentinel의 바이트 보존, PATH 링크를 통해 새 실행 파일 실행, update 임시 폴더·잠금 제거 확인.
- 로컬 서버 요청 7회. 공개 릴리스 다운로드 검증 요청 0회, AFO 운영 사이트/API 검증 요청 0회. 코드 조사용 GitHub 메타데이터 조회와 Node.js 빌드 런타임 다운로드는 제품 경로 검증이 아닙니다.
