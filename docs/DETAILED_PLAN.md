## 2. MVP 확정안

MVP는 **필수 13개 기능**이다. 권장 4개는 일정 여유가 있을 때만 하고, 제외 목록은 첫 버전에서 만들지 않는다. 필수 기능의 완료는 화면 문구가 아니라 테스트 폴더의 실제 파일 상태로 판정한다.

**일정이 밀릴 때**: 13.2절의 날짜별 게이트(G0\~G7)로 판단한다. 축소 순서는 권장 작업(S1 → S3 → S2 → S5 → S4 축소) → F13 되돌리기 → 규칙 관리 화면 단순화 → 개인화 조합 규칙(단일 특징 규칙만 유지) → 두 번째 OS의 실행 기능(분석·미리보기 전용으로 전환) 순이다. 최소 시연 가능 버전(MVD, 13.1)에 든 기능은 줄이지 않는다.

## 3. 기술 스택 결정

**Electron + TypeScript를 확정한다.** 기획서가 제시한 스택이고, 휴지통 API(`shell.trashItem`)가 내장되어 있으며, 분류 엔진을 순수 TypeScript로 쓰면 같은 코드를 브라우저 시연 페이지에서도 돌릴 수 있다. 이 마지막 점이 제출 URL 조건(15절)에 대한 가장 큰 이점이다.

### 4.4 planHash 정규화와 결정성 \[2차 수정\]

결정성은 **계획 내용(`PlanContent`)에 대해서만** 요구한다. `planId`와 `createdAt`은 봉투에 두고 해시·결정성 비교에서 뺀다. 같은 파일 상태에서 계획을 두 번 만들면 `planHash`는 같고 `planId`는 다르다. 승인은 둘을 모두 기록하므로, 같은 내용이라도 다른 계획에 이전 승인을 쓸 수 없다.

1. **직렬화**: 키를 UTF-16 코드 단위 순으로 정렬한 JSON, 공백 없음, UTF-8(RFC 8785 JCS 방식). 라이브러리 사용 여부는 C-1에서 결정한다.
2. **숫자**: 정수만 넣는다. 크기는 바이트 정수, `mtimeNs`·`dev`·`ino`는 10진 문자열(2^53을 넘을 수 있음). 확신도 같은 소수는 해시 대상에 넣지 않는다.
3. **문자열**: NFC 정규화. 경로는 루트 기준 상대 경로, 구분자 `/`, 앞뒤 `/` 없음. `targetRoot`는 `realpath` 결과를 NFC로 바꾼 값.
4. **배열 순서**: `items`는 op 순서(move → trash → delete), 그다음 `srcRelPath`의 코드 단위 비교. 로캘에 따라 결과가 바뀌는 `localeCompare`는 쓰지 않는다.
5. **itemId**: `sha256(op + "\u0000" + srcRelPath)`의 앞 16자(16진).
6. **해시 대상**: `schemaVersion, engineVersion, targetRoot, options`(보호 시간·임계값을 정수로), `rulesetHash`, 각 item의 `itemId, op, srcRelPath, dstRelPath, preState, ruleId, userEdited`.
7. **해시 제외**: `planId, createdAt, rootHandle`, `reasonText`·후보 목록·확신도 같은 표시용 값, 스캔 소요 시간.
8. **rulesetHash**: 활성 규칙을 `id`순으로 정렬해 같은 방식으로 해시(`stats.examples` 같은 표시용 값 제외).

결정성의 범위: "같은 입력"은 **같은 파일 시스템 상태**(같은 inode·수정 시각)를 뜻한다. 폴더를 복사해 만든 사본은 inode·시각이 달라 다른 입력으로 본다.

| ID | 테스트 | 통과 기준 |
| --- | --- | --- |
| T-DET-1 | 같은 폴더 상태에서 계획 2회 | `PlanContent` 바이트·`planHash` 동일, `planId` 다름 |
| T-DET-2 | 파일 1개의 수정 시각 변경 후 재계획 | `planHash` 변경 |
| T-DET-3 | 이유 문장 생성 규칙만 변경 | `planHash` 불변 |
| T-DET-4 | NFD 파일명이 섞인 폴더 | 정규화·정렬 결과가 NFC 기준과 같음 |
| T-DET-5 | 로캘·시간대 환경 변수를 바꿔 계획 | `planHash` 동일 |
| T-DET-6 | 같은 내용으로 다시 만든 계획(다른 `planId`)에 이전 승인 사용 | 거부 |

## 5. 이름 충돌·덮어쓰기 방지 설계

결론: **실행기는 `fs.rename`을 쓰지 않는다**(대상이 있으면 조용히 덮어쓰기 때문\[연구 7절\]). MVP의 이동은 **같은 볼륨 안에서 하드 링크로 새 이름을 만든 뒤 원본 이름을 지우는 한 가지 방식**만 쓴다. `fs.link`는 대상이 있으면 `EEXIST`로 실패하므로 덮어쓰기가 원리적으로 불가능하고, 내용을 복사하지 않으므로 부분 복사가 생기지 않는다. 각 단계 전에 저널을 디스크에 기록해, 어느 시점에 중단되더라도 "원본 그대로" 또는 "이동 완료" 중 하나로 정리한다(5.5). 다른 볼륨·링크 미지원 볼륨으로의 이동은 MVP에서 실행하지 않고 건너뛴다. 목적지가 정리 폴더 안으로 제한되므로\[기획서 M4\] 이런 경우는 하위 폴더가 다른 드라이브에 연결됐거나 정리 폴더 자체가 FAT·exFAT일 때만 생긴다. 복사 방식은 권장 S5로 옮겼다. \[2차 수정\] **(검증 필요, SPK-2)**

### 5.1 계획 단계(충돌을 미리 없앰)

1. 이름 비교 키를 `NFC 정규화 + 대소문자 무시`로 만든다. Windows와 macOS 기본 파일 시스템은 대소문자를 구분하지 않고, macOS에서 만든 한글 파일명은 NFD로 저장될 수 있기 때문이다.
2. 목적지 폴더의 기존 파일과 같은 계획 안의 다른 항목을 함께 보고, 겹치면 `이름 (1).ext`, `이름 (2).ext` 순으로 새 이름을 정한다. 이름이 바뀐 항목은 계획 표에 "이름 변경됨" 배지를 단다. 계획 표에 보이는 최종 경로가 곧 승인 대상이다(6.3).
3. 경로 문제는 실행 대상에서 빼고 "경로 문제"로 표시한다: Windows 예약 이름(CON, PRN, AUX, NUL, COM1 등), 금지 문자(`<>:"/\|?*`), 끝의 점·공백, 260자 이상 경로(Windows), 목적지 폴더 이름과 같은 파일이 이미 있는 경우.
4. 폴더 자체는 이동하지 않는다. 폴더는 만들기만 한다.

### 5.2 실행 단계(항목 하나의 처리 순서)

**보존 불변식**: 어느 시점에 중단되더라도, 실행 전 각 파일의 내용은 **원래 경로 또는 승인된 목적지 중 최소 한 곳**에 남아 있어야 한다. 예외는 사용자가 승인한 휴지통 이동·영구 삭제 항목뿐이다. 모든 단계 설계와 실패 주입 테스트(5.6)는 이 불변식을 기준으로 한다.

**이동(링크 방식)** — 저널 기록은 해당 동작 **전에** 쓰고 `fsync`한다.

| 단계 | 저널 | 동작 | 실패·예외 처리 |
| --- | --- | --- | --- |
| M0 사전 확인 | — | 원본 `lstat`을 `preState`(크기·`mtimeNs`·`dev`·`ino`)와 비교. 목적지 폴더 생성 후 실제 경로가 루트 안·참고 폴더 밖인지, 원본과 같은 `dev`인지 확인 | 불일치 → "승인 후 변경됨", 다른 `dev` → "지원하지 않는 드라이브"로 건너뜀(`skipped`) |
| M1 링크 | `intent{src, approvedDst, srcIno}` | `fs.link(src, approvedDst)` | `EEXIST` → 6.3 정책(기본: 건너뜀). `EPERM`·`ENOTSUP`·`EXDEV` → "링크 미지원"으로 건너뜀 |
| M2 링크 확인 | `linked{actualDst}` | 목적지의 `ino`가 `srcIno`와 같은지 확인 | 다르면 목적지를 건드리지 않고 `needs-check` |
| M3 원본 재확인 | — | 원본 경로의 `ino`가 아직 `srcIno`인지 확인 | 다르면(편집기가 "새 파일로 저장"해 원본이 교체됨) 원본은 그대로, 목적지(이전 내용)도 보존하고 "원본 변경됨: 두 파일 보존"으로 끝냄 |
| M4 원본 이름 제거 | — | `fs.unlink(src)` | `EBUSY`·`EPERM`(다른 앱이 사용 중) → **롤백**: 목적지 `ino`가 `srcIno`인지 확인 후 목적지 이름만 제거, "사용 중"으로 건너뜀 |
| M5 완료 | `done` | 원본 경로가 비었고 목적지 `ino`가 `srcIno`인지 확인 | 확인 실패 → `needs-check` |

M3에서 `ino`가 같고 수정 시각만 바뀐 경우(같은 파일을 제자리에서 편집)는 두 이름이 같은 내용을 가리키므로 그대로 진행해도 잃는 것이 없다. **잔여 위험**: M3와 M4 사이의 아주 짧은 순간에 다른 프로그램이 원본 이름을 새 파일로 바꾸면, 이름 기준 삭제의 한계로 그 새 파일이 지워질 수 있다. 최근 24시간 수정 파일 보호(N1)와 M3 재확인으로 가능성을 낮추고 16절에 기록한다.

**휴지통 이동**

| 단계 | 저널 | 동작 | 실패·예외 처리 |
| --- | --- | --- | --- |
| T0 사전 확인 | — | `preState`와 비교하고 SHA-256을 다시 계산(중복 판정의 근거가 해시이므로) | 불일치 → 건너뜀 |
| T1 휴지통 | `intent` | `shell.trashItem(src)` | 거부 → `failed`, 원본 그대로 |
| T2 확인 | `done` | 원본 경로가 비었는지 확인 | 남아 있으면 `failed` |

S5(권장) 복사 방식을 구현할 때의 원칙: 원본은 마지막까지 건드리지 않고, 목적지 폴더 안의 고유한 임시 이름(`.afo-<runId>-<itemId>.part`)에 `COPYFILE_EXCL`로 복사한 뒤 SHA-256을 검증하고, 링크(또는 다시 `COPYFILE_EXCL`)로 최종 이름에 올린다. 최종 이름에는 완전한 내용만 나타나므로 부분 복사가 최종 이름으로 남지 않는다. 원본 제거 직전에 원본의 `ino`·크기·수정 시각을 다시 확인하고, 복사 중 원본이 바뀌었으면 두 파일을 모두 보존한다.

### 5.5 상태별 복구 정책(재시작 시 정합 복구) \[2차 수정\]

판정은 저널이 아니라 **파일 시스템의 실제 상태**로 한다. 저널은 어느 항목을 볼지만 알려 준다. 판정이 확실하지 않으면 아무것도 지우지 않고 `needs-check`로 남긴다.

| 마지막 저널 상태 | 파일 시스템 관찰 | 판정 | 복구 동작 |
| --- | --- | --- | --- |
| `intent`(이동) | 목적지 없음, 원본이 `preState`와 같음 | 링크 전 중단 | 없음 → "미실행" |
| `intent`·`linked` | 목적지 `ino` = `srcIno`, 원본도 같은 `ino` | 링크 후·원본 제거 전 중단 | M3 재확인 후 원본 이름 제거로 마무리 → `done` |
| `intent`·`linked` | 목적지 `ino` = `srcIno`, 원본 경로에 다른 `ino` | 중단 중 원본이 교체됨 | 둘 다 보존 → "원본 변경됨" |
| `intent`·`linked` | 원본 없음, 목적지 `ino` = `srcIno` | 원본 제거 후·기록 전 중단 | 기록만 `done` |
| `intent` | 목적지가 있으나 `ino` ≠ `srcIno` | 다른 프로그램의 파일 | 목적지 손대지 않음 → "미실행" |
| 모든 상태 | 원본·목적지 모두 없음 등 표에 없는 조합 | 예상 밖 | 아무것도 하지 않음 → `needs-check`, 감사 경고 |
| `intent`(휴지통) | 원본 없음 | 휴지통 이동 완료 추정 | `done`(추정) + 휴지통 확인 안내 |
| `intent`(휴지통) | 원본 있음 | 미실행 | 없음 |

**재실행 규칙**

1. 정합 복구는 저널에 `intent` 이상이 기록된 항목만 다룬다. 시작되지 않은 항목은 이어서 실행하지 않고 "미실행"으로 끝낸다. 그사이 파일이 바뀌었을 수 있으므로 사용자가 다시 계획·승인해야 한다.
2. 정합 복구가 끝나면 승인은 `closed`가 되어 다시 쓸 수 없다.
3. 정합 복구는 멱등이다. 복구 도중 다시 중단되어도, 두 번 실행해도 결과가 같다.
4. 저널의 마지막 줄이 잘려 있으면(쓰는 중 중단) 그 줄을 버린다. 기록은 동작 전에 쓰므로 줄이 없으면 그 동작도 시작되지 않았거나, 파일 시스템 관찰로 판정할 수 있다.

## 6. 승인 범위와 실제 실행의 일치 검증

결론: 일치는 **다섯 겹**으로 보장한다. 렌더러가 경로를 보낼 수 없는 구조, 해시로 고정된 승인 기록, 항목마다의 실행 직전 검사, 한 번만 실행되는 승인, 그리고 실행기와 다른 사람이 작성한 **감사기(auditor)** 가 실행 전후 파일 상태를 비교해 "승인 밖 변경 0건"을 확인하는 것이다. 마지막 단계는 실행기 코드에 버그가 있다는 전제로 둔다. \[기획서 6절 + 신규\]

| 단계 | 시점 | 검사 내용 | 실패 시 |
| --- | --- | --- | --- |
| L1 구조 | 항상 | 렌더러는 `rootHandle`·`planId`·`itemId`만 보냄. IPC 입력은 스키마로 검사하고 모르는 필드는 거부. 실행기는 작업 종류(op)와 경로를 저장된 계획에서만 읽음 | 요청 거부 |
| L2 승인 기록 | `approve` 호출 | `planHash`를 `PlanContent`에서 재계산해 일치(4.4), `planId`도 일치, 승인 ID ⊆ 계획 항목(중복 없음), 영구 삭제 ID ⊆ 승인 ID이면서 op가 `delete`이고 별도 확인 입력 완료(S1), 새 규칙 ID ⊆ 계획의 규칙 후보, **`onRuntimeConflict` 값이 `skip`·`suffix` 중 하나**. 통과하면 `Approval`을 원자적으로 저장 | 승인 생성 안 됨, 사유 표시 |
| L3 항목 실행 직전 | 항목마다 | 승인 기록에 포함, 원본·목적지의 실제 경로가 정리 대상 루트 안이고 참고 폴더 밖, 원본이 링크 아님, `preState` 일치, **실제로 쓸 목적지가 승인 경로이거나 6.3 정책이 허용한 이름**, 현재 규칙으로 다시 분류한 결과가 계획과 같음(사용자가 직접 지정한 항목은 제외) \[기획서 M2\] | 해당 항목만 건너뜀(사유 기록) |
| L4 1회 실행 | `execute` 호출 | 승인 상태가 `open`일 때만 실행, 시작 시 `executing`, 끝나면 `closed`. 저널에 미완료가 있으면 새 실행 대신 정합 복구(5.5)로 진입 | 거부 또는 복구 화면 |
| L5 사후 감사 | 실행 종료·정합 복구 후 | 실행 시작 때 찍은 스냅샷과 종료 후 스냅샷 비교(6.1) | 결과 화면에 "검증 경고", 테스트 실패 |

### 6.1 사후 감사 규칙 \[신규\]

감사기는 `tools/eval`과 같은 스냅샷 비교기를 쓰며, 입력은 실행 전 스냅샷·실행 후 스냅샷·승인 기록·저널이다.

1. 사라진 경로마다 `done` 상태의 승인 항목이 하나씩 있어야 한다(이동의 원본 또는 휴지통·삭제 대상).
2. 새로 생긴 경로마다 `done` 상태 이동 항목의 `actualDst`가 하나씩 있어야 하고, 크기·해시가 사라진 원본과 같아야 한다. **`actualDst`는 승인 경로와 같거나, 승인 기록의 정책이 `suffix`일 때 같은 폴더의 `이름 (n).확장자`(n ≤ 20) 형태여야 한다.** 그 밖의 경로는 경고. \[2차 수정\]
3. 실행 전부터 있던 다른 모든 파일은 경로·크기·수정 시각·inode가 그대로여야 한다(테스트에서는 SHA-256까지 비교).
4. 개수 등식: 실행 후 파일 수 = 실행 전 − 휴지통 − 영구 삭제. 이동은 개수를 바꾸지 않는다. "원본 변경됨: 두 파일 보존" 항목은 1개 증가로 따로 계산한다.
5. 실행기 임시 파일(`.afo-*`)이 남아 있으면 경고.
6. 결과 화면의 숫자는 저널이 아니라 이 감사 결과에서 가져온다.

앱 안에서는 비용을 줄이려고 실행에 관여한 항목만 해시를 계산하고 나머지는 메타데이터로 비교한다. 테스트에서는 전체 해시를 쓴다.

### 6.3 실행 중 이름 충돌과 승인 범위 \[2차 수정\]

**승인되는 것은 계획 표에 보인 정확한 목적지 경로다.** 계획 단계에서 알 수 있는 충돌은 이미 `(1)` 같은 이름으로 정해져 표에 보이고, 그 이름 그대로 승인된다(5.1). 문제는 계획 후 실행 전에 다른 프로그램이 같은 이름을 만드는 경우뿐이며, 이때의 처리 방식도 승인 기록에 함께 넣는다.

| 정책 | 선택 방법 | 실행 중 충돌 시 | 허용되는 실제 목적지 |
| --- | --- | --- | --- |
| `skip`(기본) | 기본값 | 그 항목을 실행하지 않고 "실행 중 이름 충돌"로 표시. 다시 계획하면 새 이름으로 승인 가능 | 승인 경로와 정확히 같은 경로만 |
| `suffix` | P4 승인 확인 창에서 "충돌하면 번호를 붙여 이동"을 사용자가 켬 | 같은 폴더에서 `이름 (n).확장자`로 다시 시도(n ≤ 20) | 승인 경로, 또는 같은 폴더의 `이름 (n).확장자` |

계약 변경 요약: `PlanItem.dstRelPath`는 정확한 최종 경로, `Approval.onRuntimeConflict` 추가, `JournalEntry`에 `approvedDst`와 `actualDst`를 분리 기록, 실행기 L3와 감사 규칙 2가 허용 집합을 검사, 결과 화면은 승인 경로와 다르게 옮겨진 항목에 "번호를 붙여 이동함" 배지를 단다. 허용 집합은 실행기가 계획과 승인 기록에서 계산하며 렌더러가 보낸 값은 쓰지 않는다.

## 7. 개인화 임계값·정확도 실험 설계

결론: 임계값(`support`, `confidence`)은 **합성 데이터로 고르고, 팀원 실제 폴더로 확인하며, 따로 떼어 둔 데이터로 최종 보고**한다. 채택 기준은 "잘못 옮기는 비율 5% 이하를 지키면서 자동 분류율이 가장 높은 조합"이다. 이 기준값(5%)은 팀 합의 사항이다. 실험은 10/30에 평가 도구를 완성하고, 규칙 추출기(E-6, 10/31)와 통합(I-1) 이후인 11/2에 임계값을 확정한다(EV-1). 그전까지는 초기값(support ≥ 3, confidence ≥ 0.8)을 쓴다. \[연구 9.8 구체화\]

### 7.1 데이터셋

| ID | 내용 | 규모 | 용도 | 개인정보 |
| --- | --- | --- | --- | --- |
| D1 | 합성 폴더 생성기: 사용자 유형 4종(학생 과목·학기, 사진 연/월, 영수증·서류, 프로젝트), 파일명 잡음 수준 3단계(키워드 누락·오타·`scan_0012` 같은 무의미 이름 비율), 한글·영문 혼합, NFD 파일명 포함. 정답 폴더를 함께 출력 | 시드별 500\~2,000개 | 임계값 탐색(개발용 시드), 회귀 테스트(CI) | 없음 |
| D2 | 팀원 2명이 이미 정리해 둔 실제 폴더 | 각 200개 이상 목표 | 실제 분포 확인 | 평가 도구는 로컬 실행, 지표 숫자만 기록·커밋 |
| D3 | 외부 사용자 1\~2명 폴더(동의 시) 또는 D1의 별도 시드 | 200개 이상 | 최종 보고용(튜닝에 사용 금지) | D2와 동일 |

### 7.2 실험 절차

1. **분할**: 각 폴더를 수정 시각 기준 앞 80%(규칙 추출용)와 뒤 20%(평가용)로 나눈다. 보조로 무작위 5분할도 돌려 결과가 분할 방식에 민감한지 본다. \[연구: Bekkerman 2004\]
2. **비교군**: B0 확장자 규칙만 / B1 기본 규칙(확장자+파일명) / B2 B1+개인화 규칙 / B3 B2+미분류 상위 3개 후보(S2).
3. **탐색 격자**: `support ∈ {2, 3, 5}` × `confidence ∈ {0.6, 0.7, 0.8, 0.9}` × 조합 깊이 `{1, 2}` = 24개 조합.
4. **지표**(평가용 파일 기준)
   - 자동 분류율 = 이동 결정이 난 파일 / 전체
   - 정밀도 = 올바른 폴더로 결정된 파일 / 이동 결정 파일
   - 잘못된 이동률 = 1 − 정밀도 (사용자가 고쳐야 하는 비율)
   - 미분류 상위 3개 적중률(B3)
   - 제안 규칙 수(사용자 검토 부담)
5. **선택**: D1 개발 시드에서 잘못된 이동률 ≤ 5%를 만족하는 조합 중 자동 분류율이 가장 높은 것을 고른다. 동률이면 규칙 수가 적은 쪽.
6. **확인**: D2에서 같은 조합이 기준을 지키는지 본다. 크게 어긋나면 D2를 보고 조정하지 않고 원인(파일명 잡음, 폴더 깊이)을 기록한다.
7. **보고**: D3에서 B0 대비 B2의 차이를 95% 신뢰구간(Wilson)과 함께 발표 자료에 쓴다. 평가 파일이 200개면 신뢰구간 폭이 대략 ±5\~7%p라는 점을 같이 밝힌다.

### 7.3 자동화와 산출물

- `npm run eval -- --dataset d1 --grid` → `eval-report.json`과 표 형태 요약 출력. 같은 시드면 같은 결과(결정성 확인).
- CI는 D1 고정 시드 1개로 B2를 매 PR마다 돌려, 정밀도가 기준 대비 2%p 넘게 떨어지면 실패 처리한다(알고리즘 회귀 방지).
- 결과는 `docs/eval/YYYY-MM-DD.md`에 기록하고, 임계값 변경은 이 기록을 링크한 PR로만 한다.

### 7.4 이 실험으로 알 수 없는 것

합성 데이터의 사용자 유형은 팀이 상상한 분포이므로 실제 사용자와 다를 수 있다. 실제 만족도는 11/4 외부 사용자 테스트(수정한 항목 수, 소요 시간, 잘못된 변경 여부 관찰)로만 확인한다\[기획서 11절\].

### 8.2 CI와 실제 기기의 구분

GitHub 호스팅 러너는 화면 없는 가상 머신이라 휴지통·권한 요청 동작이 실제 기기와 다를 수 있다. 그래서 휴지통·권한 관련 테스트는 **CI에서는 어댑터를 가짜로 바꿔 논리만 검사**하고, 실제 동작은 팀원 기기에서 수동 체크리스트로 확인해 `docs/verification/`에 "VM" / "실제 기기"를 구분해 기록한다\[기획서 10절\]. 팀원 각자의 운영체제(누가 Windows, 누가 macOS를 가졌는지)는 합의 사항에서 확정한다.

- **검토 필요**: 미분류·규칙 충돌 항목. 기본 미선택. 상위 3개 후보(S2)나 직접 선택으로만 이동 \[기획서 "모호한 항목만 검토 대상"\].

- **보호·제외**: 최근 수정, 링크·바로가기, 숨김, 경로 문제, 권한 없음. 사용자가 최근 수정 항목만 포함으로 돌릴 수 있음.

## 10. Claude Code 하네스 구조

결론: 기획서의 4개 역할을 유지하되, **조정 담당은 별도 에이전트가 아니라 개발자가 직접 운영하는 메인 Claude Code 세션**으로 두고, 서브에이전트는 파일 엔진·화면·검증 세 개만 만든다. 편집 범위는 지침 문서가 아니라 **훅으로 기계적으로 막는다.** CLAUDE.md는 맥락일 뿐 강제되지 않기 때문이다.

&#91;embedded content: 작업 흐름 · 구현과 검증 분리, 실패 시 되돌아감\]

구현 에이전트의 결과는 훅·CI를 거쳐 검증 에이전트가 판정하고, 통과한 변경만 상대 개발자가 리뷰해 병합한다. 실패는 기록한 뒤 같은 Issue에서 다시 구현한다.

### 10.1 Claude Code 실제 기능과 이 계획의 사용법

아래 “실제 기능”은 Claude Code 공식 문서(code.claude.com/docs)에서 2026-10-26에 확인한 것이고, “설계 아이디어”는 그 기능들을 조합한 우리 규칙이다.

| 기능 | 실제 동작(확인) | AFO 사용법(설계 아이디어) |
| --- | --- | --- |
| CLAUDE.md | 루트·상위 폴더는 시작 시, 하위 폴더 CLAUDE.md는 그 폴더 파일을 읽을 때 로드. `@경로`로 다른 파일 가져오기 | 루트 CLAUDE.md는 200줄 이내, 패키지별 CLAUDE.md에 국소 규칙 |
| AGENTS.md | Claude Code가 자동으로 읽지 않음. CLAUDE.md 첫 줄에 `@AGENTS.md`로 가져오기 | 도구 중립 규칙은 AGENTS.md, Claude 전용 운영은 CLAUDE.md |
| 서브에이전트 | `.claude/agents/*.md`, 필수 `name`·`description`, 선택 `tools`·`disallowedTools`·`model`·`hooks`·`isolation: worktree` 등. **경로별 편집 제한 필드는 없음** | 역할별 에이전트 3개, 경로 제한은 에이전트 전용 PreToolUse 훅으로 |
| 권한 규칙 | `.claude/settings.json`의 allow·ask·deny, `Edit(/경로/**)` 형식. deny가 항상 우선. Bash 규칙은 문자열 매칭이라 보안 경계가 아님 | `packages/contracts/**` 편집은 ask, `.claude/**`·CI 설정 편집은 deny(사람만 수정) |
| 훅 | PreToolUse는 종료 코드 2 또는 JSON `deny`로 도구 차단. Stop·SubagentStop은 `decision: block`으로 종료를 막고 계속 작업 지시 가능 | 경로 가드, 편집 후 타입 검사, 종료 전 빠른 테스트(아래 10.3) |
| 스킬(슬래시 명령) | `.claude/skills/<이름>/SKILL.md` → `/이름`. 기존 `.claude/commands/`도 동작 | `/issue-start`, `/verify`, `/pr-ready`, `/record-failure` |
| 워크트리 | `claude -w <이름>` → `.claude/worktrees/<이름>/`, 에이전트의 `isolation: worktree` | Issue마다 별도 작업 폴더, 동시 구현은 최대 2개 \[기획서 7절\] |
| Plan 모드 | 계획 승인 전 편집 차단 | 실행기·계약 변경 Issue는 Plan 모드로 시작 |
| 헤드리스 `claude -p` | JSON 출력, 허용 도구 지정, CI 사용 가능 | 선택: 야간 회귀 점검. 기본 계획에는 넣지 않음 |
| GitHub Actions | `anthropics/claude-code-action@v1`, `@claude` 멘션, API 키·Actions 시간 비용 발생 | **합의 사항.** 비용·키 관리 부담으로 기본은 미사용 |
| `/init`, `/review` | CLAUDE.md 초안 생성, `/review`는 `/code-review` 스킬 별칭 | 초기 CLAUDE.md 초안, PR 자체 리뷰 보조 |

확인하지 못한 것: settings의 deny 규칙이 서브에이전트 실행에도 적용되는지(H-1 작업에서 직접 시험), SessionStart 훅 출력이 맥락으로 들어가는지, output style.

| --- | --- | --- | --- | --- |

### 10.5 우선순위(규칙 충돌 시)

1. 개발자가 현재 세션에서 한 직접 지시
2. 해당 Issue의 수용 기준
3. 역할 지침(`.claude/agents/*.md`)
4. 패키지별 CLAUDE.md
5. 루트 AGENTS.md·CLAUDE.md의 일반 규칙

예외 절차: 직접 지시가 AGENTS.md의 **안전 불변식**(실제 사용자 폴더 테스트 금지, 덮어쓰기 금지, 승인 밖 변경 금지 등)과 충돌하면, 에이전트는 충돌을 밝히고 한 번 확인을 받은 뒤 따르며, PR 본문에 예외를 기록한다. 훅은 지시로 끌 수 없고 `.claude/` 변경 PR로만 바뀐다.

### 10.6 실패 기록과 반영

1. 검증 실패·리뷰 지적·수동 테스트 결함은 `/record-failure`로 `docs/harness/failures.md`에 한 줄씩 남긴다.
2. 같은 결함을 잡는 회귀 테스트를 검증 에이전트가 추가한다.
3. 같은 종류가 2회 생기면 AGENTS.md "알려진 함정"에 규칙 한 줄을 추가하고, 기계적으로 막을 수 있으면 훅이나 린트 규칙으로 옮긴다.
4. `/issue-start`는 해당 패키지의 최근 실패 기록 5개를 읽고 시작한다.

### 10.7 외부 독립 검토(ChatGPT) \[2차 수정\]

Claude Code 내부 검증과 별개로, **다른 회사 모델인 ChatGPT가 같은 자료를 독립적으로 검토**한다. 같은 계열 모델끼리는 같은 맹점을 공유할 수 있기 때문이다. 외부 검토는 자동 테스트를 대체하지 않는다. 검토 의견은 "가설"로 다루고, 테스트로 재현된 것만 코드에 반영한다.

| 시점 | 대상 | 검토 자료(패킷) | 질문 초점 |
| --- | --- | --- | --- |
| 중요 설계 변경 | ER-1(이 계획의 4.2·4.4·5·6절), 이후 `contract-change` PR 전부 | 설계 발췌, 변경 전후 계약 | 빠진 상태·시나리오, 불변식이 깨지는 경우, 모호한 정의 |
| 파일 실행기 PR | X-1·X-2·X-3·X-4와 S1·S5의 **모든 PR**(ER-2는 X-1·X-3 상태 기계를 묶어 보는 대표 검토) | PR 차이(diff), 수용 기준, 테스트·FI·감사 결과 | 데이터 유실 경로, 경합 조건, 테스트가 놓친 경우 |
| 통합 테스트 | ER-3(I-2 결과) | 실제 기기 체크리스트, 감사 보고, FI 결과 요약 | 누락 시나리오, 결과 해석 오류 |
| 릴리스 | ER-4(R-1 전에 1회, R-2 전에 변경분만) | 릴리스 노트, 알려진 문제, 설치 안내, 테스트 요약 | 출시를 막아야 할 위험 |

**절차**

1. 해당 코드·문서를 **작성하지 않은 개발자**가 수행한다.
2. 패킷을 만든다(H-2의 `/external-review-packet` 스킬, 그 전에는 템플릿으로 수동). 실제 사용자 파일명·경로, API 키, 개인정보는 넣지 않고 합성 데이터 이름만 쓴다.
3. 이전 맥락이 없는 새 대화에서 검토하고, 사용한 모델과 날짜를 기록한다.
4. 지적을 **차단·수정·참고**로 분류해 `docs/reviews/ER-<번호>.md`(PR 단위면 `ER-PR<번호>.md`)에 남기고 PR에 링크한다.
5. 차단·수정 지적은 먼저 재현하는 테스트를 만들고 고친다. 재현되지 않으면 근거를 적고 "재현 불가"로 닫는다. 차단 지적을 기각하려면 두 사람이 합의해야 한다.
6. 병합 조건은 그대로다: CI 통과 + 상대 개발자 승인 + (대상 PR이면) 외부 검토 기록. 외부 검토가 "문제 없음"이어도 테스트가 실패하면 병합할 수 없다.

대상 PR에는 `needs-external-review` 라벨을 붙이고, PR 템플릿의 외부 검토 칸이 비어 있으면 리뷰어가 승인하지 않는다(GitHub가 강제할 수 없는 수동 규칙). 소요 시간은 ER Issue와 각 실행기 Issue의 예상 시간에 포함했다(12절).

### 11.3 규칙

| 항목 | 규칙 |
| --- | --- |
| 브랜치 | `main`(보호) ← `feat/<이슈번호>-<짧은이름>`, `fix/…`, `spike/…`, `harness/…`, `docs/…`. 예: `feat/14-no-clobber-move`. 에이전트 워크트리 브랜치도 같은 이름 사용 |
| Issue 템플릿 | 배경 · 편집 허용 경로 · 선행 Issue · **수용 기준(측정 가능한 체크박스)** · 테스트 ID · 담당 · 예상 시간 · 라벨(`area:*`, `type:*`, `priority:must/should`) |
| PR 템플릿 | `Closes #n` · 변경 요약 · 실제 편집 경로 · 테스트 증거(실행 명령과 결과) · 스냅샷 감사 결과(실행기·감사 관련 시) · 화면 스크린샷(UI 시) · 외부 검토 기록 링크 또는 "해당 없음"(10.7) · 위험·남은 일 |
| 크기 | PR 하나는 Issue 하나, 변경 400줄 이하 권장(테스트·픽스처 제외) |
| 검토 | 상대 개발자 1명 승인 필수(CODEOWNERS). `executor`·`audit`·`contracts` 변경은 검증 에이전트 보고서 첨부 필수, executor·contracts 변경은 외부 검토 기록도 필수(10.7) |
| 병합 | 스쿼시 병합, CI 전부 통과 후. 병합 후 브랜치 삭제 |
| 공용 계약 변경 | `contract-change` 라벨 Issue → `packages/contracts`와 필요한 최소 수정만 담은 PR → **두 사람 모두 승인** → 스키마 버전 올림 → 그날 안에 상대방 브랜치 리베이스. 계약 PR이 열려 있는 동안 다른 계약 PR 금지 |
| 충돌 해결 | 매일 22:00 각자 `main` 리베이스. 공용 파일(`package.json`, lockfile, CI)은 변경 전 메신저로 알림. lockfile 충돌은 `main` 기준으로 받은 뒤 `npm install` 재생성. 같은 파일 충돌이 반복되면 소유권 재조정을 다음 날 아침 회의에서 결정 |

## 12. GitHub Issue 단위 작업 분해

2차 재평가 결과 작업은 **48개 Issue**다(실행기 복구·실패 주입·외부 검토 추가, 되돌리기·하네스 확장 분리, 복사 방식은 권장으로). 각 Issue는 단계 라벨을 가진다: **MVD**(11/2까지, 13.1), **MVP**(11/4까지), **권장**(여유 시).

|  | 구민준 | 장민서 | 가용(하루 5시간) | 가용(하루 3시간) |
| --- | --- | --- | --- | --- |
| MVD 작업(11/2까지) | 36h | 33.5h | 각 38h(10/26 3h + 7일 × 5h) | 각 약 23h |
| MVP 나머지(11/3\~5) | 11.5h | 13.5h | 각 14h | 각 약 9h |
| 필수 합계 | 47.5h(91%) | 47h(90%) | 각 52h | 각 약 32h |
| 권장 | 7.5h | 4h | 남는 시간 거의 없음 | 불가 |

**판단**: 하루 5시간이면 필수 작업은 들어가지만 여유가 10% 안팎이라 권장 작업은 G2(10/29) 재추정에서 실제 속도가 추정보다 빠를 때만 한다. **하루 3시간이면 MVD조차 11/2까지 끝나지 않는다**(각 10시간 이상 부족). 이 경우 13.2의 MVD-B로 전환한다. 가용 시간은 오늘 합의 사항 1번이다.

**소요 추정 근거**: AI 에이전트가 초안을 쓰고 사람이 지시·검토·수동 확인하는 시간을 합친 값이다. 순수 함수·데이터 작업은 1\~2시간, 실제 파일 시스템을 바꾸거나 OS별 확인이 필요한 작업은 테스트·두 OS 확인 때문에 3\~4시간, 상태가 많은 P3 화면은 5시간으로 잡았다. 실행기 Issue에는 외부 검토 0.25\~0.5시간을 포함했다. 사람의 검토 시간이 병목이므로 에이전트 병렬 수와 무관하게 사람 시간 기준으로 계산했다. 첫 3일의 실제 소요를 기록해 10/29 저녁(G2)에 재추정한다.

### 13.1 최소 시연 가능 버전(MVD) \[2차 수정\]

MVD는 **한 OS의 실제 기기에서, 생성기로 만든 샘플 폴더로** 아래 시나리오를 끝까지 보여 줄 수 있는 상태다. 실제 사용자 파일은 쓰지 않는다. 목표 시점은 11/2 22:00이며, 이 시점의 빌드만으로도 영상 촬영과 제출이 가능해야 한다.

1. 정리 폴더·참고 폴더 선택 → 스캔(F1)
2. 기본·개인화 규칙으로 계획 생성, 항목마다 이유 표시(F2·F3·F5)
3. 목적지 변경 1건("이후에도" 선택), 중복 1그룹·큰 파일 확인(F6·F7·F8)
4. 새 규칙 포함 일괄 승인 → 같은 볼륨 이동·중복 휴지통 실행(F9·F10)
5. 결과 화면 수치 = 감사 결과, 감사 경고 0(F11)
6. 실행 중 강제 종료 → 재시작 → 정합 복구(F12)
7. 재시작 후 승인한 규칙 유지(F4 저장)

MVD에서 빠지는 것: 이동 되돌리기(F13), 규칙 관리 화면(U-4), 두 번째 OS, 임계값 실험 결과(초기값 사용), 설치 파일, 외부 사용자 테스트.

## 14. 테스트·검증 계획

결론: 모든 파일 변경 테스트는 **실행 전후 스냅샷을 비교하는 한 가지 판정기**로 통과 여부를 정한다. 화면 문구나 함수의 성공 반환값은 판정에 쓰지 않는다\[기획서 10절\]. AI가 작성한 코드에 결함이 있다는 전제로, 판정기 자체도 결함 주입 테스트(T-APR-8)로 검증한다.

### 14.1 스냅샷 비교 방법

1. **스냅샷**: 루트 아래 모든 항목을 `{relPath(NFC), 종류, size, mtimeMs, ino, sha256}`로 기록하고 경로순 정렬, 파일 수·총 바이트를 함께 저장한다(JSON).
2. **차이 계산**: 실행 전후를 비교해 추가·삭제·내용 변경을 구하고, 삭제된 것과 추가된 것의 해시가 같으면 "이동"으로 묶는다.
3. **기대 변경**: 승인 기록과 저널의 `done` 항목에서 기대 이동·휴지통·삭제 목록을 만든다.
4. **판정**: 설명되지 않는 차이가 0개, 기대 변경이 모두 실제로 일어남, 파일 수 등식 성립(6.1). 하나라도 어긋나면 실패이며 차이 목록을 출력한다.

**테스트 파일과 실제 파일 분리**: 테스트 루트는 항상 `os.tmpdir()/afo-test-<무작위>` 아래에 생성기로 만든다. 테스트 도우미는 이 접두어가 아닌 경로를 받으면 즉시 예외를 던지고, 하네스 훅이 실제 홈 폴더 경로를 쓰는 명령을 막는다(10.3). 개발 중 앱의 기본 정리 폴더도 샘플 폴더로 둔다.
